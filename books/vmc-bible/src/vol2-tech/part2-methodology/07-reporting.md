# 보고와 커뮤니케이션

| 레벨 | 상태 | 최종 개정 |
|---|---|---|
| 🟡 | 🔄 개정중 | 2026-10-22 |

> **한눈에 보기**
> 고치는 사람이 10분 안에 재현할 수 있어야 좋은 보고서다. 재현 절차 · 영향 · 수정 제안 세 가지가 핵심이다.
> 보고서는 분석의 요약이 아니라 **다른 사람을 움직이는 문서**다. 읽는 사람이 무엇을 해야 하는지가 먼저다.
> 영향도는 과장도 축소도 하지 않는다. 신뢰가 깨지면 다음 보고서를 아무도 읽지 않는다.

## 1. 보고서는 누가, 어떻게 읽는가

분석가는 보고서를 **찾은 순서**로 쓰고 싶어 한다. 정보 수집에서 시작해 어떤 고생 끝에 찾았는지. 개발자는 그렇게 읽지 않는다.

```
개발자가 읽는 순서                         분석가가 쓰고 싶은 순서
─────────────────────                     ─────────────────────
① 제목: 뭐가 어디서 얼마나 심각한가        ① 배경과 분석 과정
② 재현 절차: 내 환경에서 돌려 본다          ② 발견 경위
③ (재현됨) 어느 코드인가 → 고친다           ③ 기술적 상세
④ (재현 안 됨) 보고서를 닫는다              ④ 영향
⑤ 영향: 얼마나 급한가 → 우선순위            ⑤ 재현 절차
```

②에서 ④로 가는 순간 보고서는 죽는다. 그래서 **재현 절차가 보고서의 중심**이다. [6장 5절](06-exploit-verification.md)에서 만든 재현 스크립트가 여기 들어간다. 개발자의 질문 순서에 맞추면 보고서 구조가 저절로 나온다.

독자가 둘 이상이면 버전을 나눈다. 경영진·관리자에게는 "무엇이 위험하고 언제까지 무엇을 해야 하는가" 반 쪽, 개발자에게는 재현과 코드 위치가 있는 전체본. 하나의 문서로 둘을 만족시키려 하면 둘 다 안 읽는다.

## 2. 구조 요약

상세 템플릿과 예시는 [8부 1장](../part8-reporting/01-report-structure.md)에 있다. 여기서는 각 부분이 **왜** 있는지만 적는다.

| 부분 | 답하는 질문 | 길이 | 흔한 실수 |
|---|---|---|---|
| **제목** | [심각도] [위치]에서 [영향] | 한 줄 | "보안 이슈 발견" 같은 무정보 제목 |
| **요약** | 뭐가, 어디서, 누가, 무엇을 얻는가 | 3~5문장 | 분석 과정 서술 |
| **영향** | 성공하면 기밀성·무결성·가용성 중 무엇이 얼마나 깨지는가. 전제 조건(인증, 상호작용) | 한 문단 + 심각도 | 전제 조건 누락 |
| **재현 절차** | 복사해서 실행하면 같은 결과가 나오는가 | 번호 목록 + 스크립트 | "적절한 페이로드를 넣으면" |
| **근본 원인** | 어느 파일 어느 줄에서 어떤 가정이 깨지는가 | 코드 위치 + 2~3문장 | 없음. 개발자가 다시 찾아야 한다 |
| **수정 제안** | 무엇으로 바꾸면 되는가. 임시 완화책은 무엇인가 | 코드 또는 설정 | "입력 검증을 강화하십시오" |
| **참고** | CWE, 유사 CVE, 관련 문서 | 링크 | |

제목 공식 하나만 기억한다. **"[심각도] [위치]에서 [영향]"**. 예: "[High] `/api/export` 파라미터 `path`의 경로 조작으로 서버 임의 파일 읽기". 제목만 읽어도 어느 팀이 맡을지, 오늘 할지 다음 주에 할지가 정해진다.

## 3. 영향도: 과장도 축소도 않는다

분석가는 두 방향으로 유혹받는다. 노력에 비례해 심각도를 올리고 싶고, 벤더와의 마찰을 피하려 내리고 싶다. 둘 다 보고서의 신뢰를 깎는다.

**과장의 형태와 교정**

| 과장 | 교정 |
|---|---|
| "RCE 가능" (실제로는 복귀 주소 통제까지만 확인) | "복귀 주소 통제 확인. NX·ASLR 환경에서 코드 실행은 추가 작업 필요" |
| "모든 사용자 데이터 유출" (실제로는 자기 계정 데이터 1건 확인) | "인증된 사용자가 다른 사용자 1명의 프로필을 읽음을 확인. 열거 가능 여부는 미확인" |
| 전제 조건 생략 (관리자 로그인 필요) | 제목과 요약에 전제 조건을 쓴다. CVSS의 PR(Privileges Required)이 이것이다 |
| 이론적 체인을 확정처럼 서술 | "확인함"과 "가능할 것으로 봄"을 문장마다 구분한다 |

**축소의 형태와 교정**

| 축소 | 교정 |
|---|---|
| "DoS일 뿐" (원격·무인증·서비스 데몬) | 원격에서 인증 없이 서비스가 죽으면 가용성 High다 |
| "내부망이라 괜찮음" | SSRF, 횡적 이동의 출발점이다. [1부 1장](../part1-foundations/01-what-is-vulnerability.md) |
| "보호 기법이 막아 줌" | 보호 기법은 지연이지 수정이 아니다. [4부 7장](../part4-binary/07-mitigations.md) |
| 벤더가 "기능"이라 해서 낮춤 | 판단 근거를 남기고 심각도는 영향 기준으로 매긴다 |

규칙은 하나다. **확인한 것은 확인했다고, 추정은 추정이라고 쓴다.** 확인한 범위가 좁아도 괜찮다. "여기까지 확인했고, 그 너머는 이런 이유로 가능성이 있다"가 가장 신뢰받는 문장이다. 점수 체계와 맥락 반영은 [8부 2장](../part8-reporting/02-severity.md)에서 다룬다.

## 4. 공개 일정 조율

취약점 보고는 벤더에게 보내는 순간 **시계가 돌기 시작한다**. 조율된 공개(coordinated vulnerability disclosure, CVD)는 벤더가 고칠 시간을 주되, 영원히 묻히지는 않게 하는 관행이다.

널리 인용되는 기준은 다음과 같다. 📎

| 주체 | 기본 기한 | 출처 |
|---|---|---|
| CERT/CC | 보고 후 45일에 공개. 패치 유무와 무관하되 예외 인정 | [CERT/CC Vulnerability Disclosure Policy](https://vuls.cert.org/confluence/display/Wiki/Vulnerability+Disclosure+Policy) |
| Google (응용 보안 정책) | 90일 | [Google Application Security](https://www.google.com/about/appsecurity/) |
| Google Project Zero | 90일 + 패치 후 30일(기술 상세 공개 유예). 2025년 7월 29일부터는 보고 사실 자체를 1주 안에 먼저 공개하는 시범 운영 추가 | [CyberScoop, 2025](https://cyberscoop.com/project-zero-google-zero-day-vulnerability-disclosure/) |
| 오픈소스 배포판 보안 목록(distros) | 7일 이내 선호, 최대 14일 | [OpenSSF 가이드](https://github.com/ossf/oss-vulnerability-guide/blob/main/maintainer-guide.md) |

CERT의 CVD 가이드는 이 기한을 "협상의 출발점이지 최종 기한이 아니다"라고 쓴다. 📎 [OpenSSF 가이드](https://github.com/ossf/oss-vulnerability-guide/blob/main/maintainer-guide.md)가 인용한 표현이다. 국제 표준으로는 ISO/IEC 29147(벤더의 외부 공개 절차)과 ISO/IEC 30111(벤더 내부 처리 절차)이 짝을 이룬다.

조율할 때 보고자가 지킬 것은 다음과 같다.

1. **첫 연락에 기한을 명시한다.** "90일 후 또는 패치 공개 후 30일 중 빠른 날에 공개 예정"처럼. 기한이 없으면 벤더는 움직이지 않고, 나중에 기한을 꺼내면 협박처럼 들린다.
2. **CVE 할당을 누가 할지 정한다.** 벤더가 CNA(CVE Numbering Authority)면 벤더가, 아니면 코디네이터가 한다. [1부 2장](../part1-foundations/02-cwe-cve-cvss.md)
3. **연장 요청에는 근거를 요구한다.** "패치가 복잡하다"는 근거가 될 수 있다. "지금 바쁘다"는 아니다. 진행 증거가 있으면 연장한다.
4. **악용이 확인되면 기한을 앞당긴다.** 공격자가 이미 아는 것을 사용자에게 숨길 이유가 없다.
5. **공개할 때 PoC는 영향 증명 수준으로.** [6장](06-exploit-verification.md)의 원칙은 공개 시점에도 유효하다. 패치 적용률이 낮은 시점에 무기화된 코드를 올리는 것은 사용자를 돕지 않는다.

센터는 보고자이면서 코디네이터다. 신고를 받아 제조사에 전달하고, 공개 시점을 조율하고, 보안공지를 낸다. 그 절차와 제도적 근거는 [1편 CVD/VDP](../../vol1-center/02-programs/06-cvd-vdp.md)와 [신고포상제](../../vol1-center/02-programs/05-bug-bounty.md), 공지 문안은 [3편 공유·공지 단계](../../vol3-practice/01-workflow-tech/04-advisory.md)에서 다룬다. 법적 범위는 [1부 4장](../part1-foundations/04-ethics-and-law.md)이다.

## 5. 예시: 나쁜 보고서와 좋은 보고서

같은 취약점([3부 1장 실습](../part3-web/01-sql-injection.md)의 검색 기능)을 두 가지로 쓴다.

### 5.1 나쁜 보고서

```
제목: 보안 취약점 발견

안녕하세요. 귀사 서비스를 분석하던 중 심각한 SQL 인젝션 취약점을 발견했습니다.
검색 기능에 적절한 페이로드를 입력하면 데이터베이스의 모든 정보가 유출될 수 있으며,
경우에 따라 서버 전체가 장악될 수 있습니다. 매우 위험하므로 즉시 조치 바랍니다.
자세한 내용은 요청 시 제공하겠습니다.
```

무엇이 문제인가. 제목에 정보가 없다. 위치(`/search`, 파라미터 `q`)가 없다. 재현 절차가 없어 개발자가 확인할 수 없다. "모든 정보", "서버 전체 장악"은 확인한 것인지 추정인지 알 수 없다. 수정 제안이 없다. 이 보고서를 받은 팀은 답장을 보내 다시 물어야 하고, 그 사이 시계는 돌고 있다.

### 5.2 좋은 보고서

```
제목: [High] /search 파라미터 q의 SQL 인젝션으로 users 테이블 읽기

요약
  /search?q= 의 값이 SQL 문자열에 그대로 연결된다. 인증 없이 UNION SELECT로
  users 테이블의 username, password 컬럼을 읽을 수 있음을 확인했다.
  데이터 변조·파일 접근은 시도하지 않았다(허가 범위 밖).

영향
  기밀성: 전체 사용자 계정 정보 읽기 (확인). 인증 불필요, 사용자 상호작용 불필요.
  무결성·가용성: 미확인. 스택 쿼리 지원 여부에 따라 가능성 있음.
  CVSS 3.1 (잠정): 7.5 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N)

재현 (대상: labs/web-sqli, 커밋 a1b2c3d, 2026-10-22 14:10 KST)
  1. curl -s "http://localhost:8080/search?q=%27"
     → 500, 본문에 "sqlite3.OperationalError: unrecognized token"
  2. curl -s "http://localhost:8080/search?q=%27%20UNION%20SELECT%20username,password%20FROM%20users--%20"
     → 200, 검색 결과 목록 끝에 admin 계정과 비밀번호 출력
  첨부: repro.sh (위 두 요청), response-1.txt, response-2.txt

근본 원인
  app/app.py:42  query = f"SELECT name FROM items WHERE name LIKE '%{q}%'"
  사용자 입력 q가 쿼리 문자열에 포매팅된다.

수정 제안
  db.execute("SELECT name FROM items WHERE name LIKE ?", (f"%{q}%",))
  추가로 DB 계정을 읽기 전용으로 분리하고 에러 메시지를 사용자에게 노출하지 않을 것.

참고
  CWE-89. 공개 예정일: 2027-01-20 (90일) 또는 패치 공개 후 30일 중 빠른 날.
```

차이는 길이가 아니다. 좋은 보고서도 한 화면이다. 차이는 **개발자가 다음에 할 일이 정해져 있는가**다. 1분 안에 재현하고, 42행을 열고, 제안된 줄로 바꾸고, 다시 `repro.sh`를 돌려 실패하는지 본다. 패치 검증은 [8부 3장](../part8-reporting/03-patch-verification.md)이다.

## 6. 말투와 관계

보고서의 상대는 적이 아니라 **같은 버그를 없애려는 동료**다. 그 전제가 문장에 드러나야 한다.

- 사람이 아니라 코드를 말한다. "개발자가 검증을 빠뜨렸다"가 아니라 "`q`가 검증 없이 쿼리에 연결된다".
- 판단어를 줄인다. "심각한", "치명적인", "기본적인 실수"는 심각도 표기와 CVSS 벡터가 대신한다.
- 모르는 것은 모른다고 쓴다. "미확인", "추정"이 "아마도"보다 낫다.
- 답장은 빠르게, 재촉은 근거와 함께. 벤더가 재현 실패를 알리면 환경 차이를 먼저 의심하고 함께 좁힌다.
- 공개 후에도 관계는 남는다. 다음 취약점을 그 벤더에 또 보고하게 된다.

## 체크리스트

**쓰기 전**
- [ ] 독자가 누구인지(개발자, 관리자, 코디네이터) 정했는가? 둘 이상이면 버전을 나눴는가?
- [ ] 재현 스크립트가 새 환경에서 돌아가는가? ([6장 5절](06-exploit-verification.md))

**쓰면서**
- [ ] 제목이 "[심각도] [위치]에서 [영향]" 형식인가?
- [ ] 전제 조건(인증, 상호작용, 네트워크 위치)이 요약에 있는가?
- [ ] "확인함"과 "추정"이 문장마다 구분되는가?
- [ ] 근본 원인에 파일과 줄 번호가 있는가?
- [ ] 수정 제안이 코드 또는 설정 수준인가? ("검증 강화"가 아닌가)

**보내기 전**
- [ ] 공개 예정일과 CVE 할당 주체를 적었는가?
- [ ] 실제 사용자 데이터, 자격증명이 본문·첨부에 없는가?
- [ ] PoC가 영향 증명 수준에 머물러 있는가?

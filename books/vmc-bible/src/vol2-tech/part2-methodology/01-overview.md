# 분석 방법론 개요

| 레벨 | 상태 | 최종 개정 |
|---|---|---|
| 🟢 입문 | 🔄 개정중 | 2026-10-21 |

> **한눈에 보기**
> 취약점 분석은 "정보 수집 → 위협 모델링 → 정적 분석 → 동적 분석 → 익스플로잇 검증 → 보고" 여섯 단계의 **반복**이다.
> 한 번에 끝나지 않는다. 동적 분석에서 발견한 것이 정적 분석을 다시 시키고, 검증 결과가 위협 모델을 고친다.
> 이 책의 모든 취약점 장은 이 순서를 따른다.

## 1. 여섯 단계

```
 ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
 │ ① 정보   │──>│ ② 위협   │──>│ ③ 정적   │──>│ ④ 동적   │──>│ ⑤ 익스플│──>│ ⑥ 보고   │
 │   수집   │   │  모델링  │   │   분석   │   │   분석   │   │ 로잇 검증│   │          │
 └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
       ▲              ▲              ▲              │              │
       └──────────────┴──────────────┴──────────────┴──────────────┘
                          발견한 것이 앞 단계를 다시 시킨다
```

| 단계 | 질문 | 산출물 | 장 |
|---|---|---|---|
| ① 정보 수집 | 무엇으로 만들어졌는가? | 기술 스택, 버전, 의존성 목록, 과거 CVE | [2장](02-recon.md) |
| ② 위협 모델링 | 누가 어디를 노릴 것인가? | 신뢰 경계가 표시된 데이터 흐름도, 우선순위 목록 | [3장](03-threat-modeling.md) |
| ③ 정적 분석 | 코드 어디가 의심스러운가? | 소스→싱크(입력이 들어오는 곳 → 위험한 동작이 일어나는 곳) 후보 목록 | [4장](04-static-analysis.md) |
| ④ 동적 분석 | 실제로 그렇게 동작하는가? | 재현 입력, 크래시, 응답 차이 | [5장](05-dynamic-analysis.md) |
| ⑤ 익스플로잇 검증 | 공격자가 실제로 뭘 얻는가? | 최소 PoC, 영향 증명 | [6장](06-exploit-verification.md) |
| ⑥ 보고 | 고치는 사람이 10분 안에 이해하는가? | 재현 절차 · 영향 · 수정 제안 | [7장](07-reporting.md), [보고](../part8-reporting/01-report-structure.md) |

## 2. 박스의 색

얼마나 아는 상태에서 시작하는가에 따라 단계의 비중이 달라진다.

| 모드 | 주어진 것 | 비중이 큰 단계 | 전형적 상황 |
|---|---|---|---|
| **화이트박스** | 소스 코드, 설계 문서, 자격증명 | ③ 정적 | 사내 코드 리뷰, 오픈소스 분석 |
| **그레이박스** | 일반 사용자 계정, 일부 문서 | ③ + ④ 균형 | 대부분의 모의해킹 |
| **블랙박스** | URL 또는 바이너리만 | ① + ④ 동적 | 버그바운티, 외부 평가 |

블랙박스라도 **바이너리가 있으면 디컴파일로 화이트박스에 가까워진다**. 바이너리 부의 핵심 논지다.

## 3. 시간 배분

경험상 한 대상에 쓰는 시간은 대략 이렇게 나뉜다. 절대 기준이 아니라 "어디에 시간이 새는지" 점검용이다.

| 단계 | 비중 | 흔한 실수 |
|---|---|---|
| ① 정보 수집 | 15% | 너무 빨리 건너뛴다. 알려진 CVE로 끝날 것을 처음부터 찾는다 |
| ② 위협 모델링 | 10% | 아예 안 한다. 그래서 중요하지 않은 곳에 시간을 쓴다 |
| ③ 정적 분석 | 25% | 자동화 도구 출력을 다 읽으려 한다 |
| ④ 동적 분석 | 30% | 후보 없이 무작위로 찌른다 |
| ⑤ 익스플로잇 검증 | 10% | 영향 증명을 넘어 "완전한 무기"를 만들려 한다 |
| ⑥ 보고 | 10% | 마지막 날 몰아서 쓴다. 재현 절차가 빠진다 |

## 4. 분석 노트

**재현 가능성이 전부다.** 3일 뒤의 내가, 또는 다른 사람이 같은 결과를 낼 수 있어야 한다.

노트에 항상 적는 것:

```markdown
## 2026-10-21 14:30 — /api/items?id= 파라미터

- 대상: http://target.local/api/items?id=1  (버전 2.3.1, 정보수집 노트 참조)
- 입력: id=1'  → 500, 본문에 "sqlite3.OperationalError"
- 입력: id=1 AND 1=1 → 200, 정상 / id=1 AND 1=2 → 200, 빈 배열
- 판단: Boolean 기반 블라인드 SQLi 후보. 다음: 컬럼 수 확인
- 재현: curl -s "http://target.local/api/items?id=1%27"
```

규칙:
- **시각**과 **대상 버전**을 적는다. 중간에 패치되면 결과가 바뀐다.
- **입력과 출력을 그대로** 적는다. "에러가 났다"가 아니라 에러 메시지 전문.
- **재현 명령**을 복사해서 바로 실행할 수 있는 형태로 적는다.
- "안 됐다"도 적는다. 같은 것을 두 번 시도하지 않기 위해서다.

## 5. 이 책의 장이 이 순서를 따르는 방식

웹·바이너리 부의 모든 취약점 장은 다음 섹션을 갖는다. 괄호 안이 대응하는 방법론 단계다.

1. 원리 (②: 어디서 신뢰 경계가 깨지는가)
2. 발생하는 코드 패턴 (③)
3. 탐지 방법: 정적 / 동적 (③, ④)
4. 실습 🧪 (④)
5. 익스플로잇 검증 (⑤)
6. 방어 (⑥의 수정 제안)
7. 우회 기법 🔴 (방어가 있을 때의 ④, ⑤)
8. 실제 CVE 사례 (①: 과거 사례에서 패턴 읽기)
9. 체크리스트 (③, ④, ⑥)
10. 더 읽기

즉 한 장을 읽는 것은 **그 취약점 유형에 대해 여섯 단계를 한 번 도는 것**이다.

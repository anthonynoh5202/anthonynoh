# 조치 단계: 고쳐지게 만드는 보고서

| 레벨 | 상태 | 최종 개정 |
|---|---|---|
| 🟡 | 🔄 개정중 | 2026-10-22 |

> **한눈에 보기**
> 센터는 강제 권한이 없다. "권고에 그친다"는 지적이 나오는 이유다. 📎
> 그래서 조치 단계의 기술은 **설득의 기술**이다. 10분 안에 재현되는 절차, 기업 언어로 쓴 영향, 당장 할 수 있는 완화책, 고친 뒤 스스로 확인하는 법.
> 그리고 패치가 왔을 때 **증상이 아니라 원인이 없어졌는지** 보는 눈.

## 1. 상대에 따라 다른 요청

| 상대 | 요청 내용 | 참고 |
|---|---|---|
| 국내 제조사 (보안 창구 있음) | 패치 요청, CVE 조율, 공개 일정 합의 | [유관기관](../../vol1-center/03-partners/11-external.md) 3절 |
| 국내 제조사 (창구 없음) | 대표 연락처. 재현 절차를 가장 쉽게. 완화책 먼저 | |
| 해외 제조사 | 해외 CERT 경유 또는 security@ 직접. 국내 사용자용 완화책 병행 | |
| 사용 기관 (상시 신고조치제) | 설정 변경·코드 수정·재배포 요청. 조치 시한 🔎 | [상시 신고조치제](../../vol1-center/02-programs/06-cvd-vdp.md) |
| 오픈소스 | 메인테이너 비공개 보고 (GitHub Security Advisory) | [공급망](../../vol2-tech/part5-extended/04-supply-chain.md) |

## 2. 조치 요청서의 다섯 요소

**쓰는 기술**: [보고서 구조](../../vol2-tech/part8-reporting/01-report-structure.md)

| 요소 | 기준 | 흔한 실패 |
|---|---|---|
| ① 재현 절차 | 상대가 **자기 환경에서 10분 안에** 확인 | "취약점이 있습니다"만 있고 절차가 없다 |
| ② 영향 | **상대의 언어**로. "SQL 인젝션"이 아니라 "회원 DB 전체가 인증 없이 읽힌다" | CVSS 벡터만 적는다 |
| ③ 조치 방법 | 패치 있으면 버전. 없으면 완화책 (설정, WAF 룰, 네트워크 차단, 기능 비활성) | "패치하세요" |
| ④ 검증 방법 | 고친 뒤 **상대가 스스로** 확인하는 명령이나 절차 | 없음. 그래서 "고쳤다"는 말만 돌아온다 |
| ⑤ 연락처와 시한 | 누구에게, 언제까지, 안 되면 어떻게 🔎 | 시한 없음 |

제목 공식: `[심각도] [제품 버전]의 [위치]에서 [영향]`. 예: `[High] OO솔루션 3.2.1 로그인 API에서 인증 우회`.

## 3. 완화책 고르기

**쓰는 기술**: 각 취약점 유형 장의 **6. 방어** 표 (계층: 코드 / 프레임워크 / 인프라 / 탐지)

패치가 없거나 적용에 시간이 걸릴 때, 방어 표에서 **인프라·탐지 계층**을 먼저 고른다. 코드를 못 고쳐도 할 수 있는 것들이다.

| 유형 | 즉시 가능한 완화 예 |
|---|---|
| 인젝션 계열 | WAF 룰 (우회 가능하므로 임시), DB 계정 권한 축소 |
| 인증·접근 제어 | 해당 기능 비활성, IP 제한, MFA 강제 |
| SSRF | 아웃바운드 허용 목록, 메타데이터 엔드포인트 차단 |
| 역직렬화·XXE | 해당 엔드포인트 차단, 파서 설정 |
| 바이너리 | 서비스 노출 차단, 완화 기법 활성화 확인 |

완화책은 "패치까지의 시간을 버는 것"이다. 공지에 완화책만 적고 패치 권고를 빼면 안 된다.

## 4. 패치 검증

**쓰는 기술**: [패치 검증과 재발 방지](../../vol2-tech/part8-reporting/03-patch-verification.md)

"고쳤다"는 말을 믿지 않는다.

1. **재현 절차를 다시 돌린다.** 검증 단계에서 남긴 재현 환경이 여기서 쓰인다.
2. **증상인가 원인인가.** 특정 페이로드만 막은 것(블랙리스트)인지, 입력과 코드를 분리한 것인지. [SQL 인젝션 6절](../../vol2-tech/part3-web/01-sql-injection.md)의 "하지 말아야 할 것"이 기준.
3. **변형을 시도한다.** 같은 유형의 다른 입력 지점, 인코딩 변형, 우회 기법(각 장의 **7절**).
4. **회귀 테스트로 남긴다.** 제조사에 테스트 케이스를 제안하면 재발이 줄고, 센터도 다음 버전 검증이 빨라진다.

검증 결과는 세 가지 중 하나로 기록한다. `충분 / 불충분(변형 남음) / 미해결`. 불충분이면 요청서를 다시 보낸다. 반복 횟수에 제한을 두지 않는다. "개선은 권고에 그친다"는 지적에 대한 센터의 답은 추적의 끈기다.

## 5. 중소기업과 외주 소멸 제품

[기업 기술지원](../../vol1-center/02-programs/08-assessment-support.md) 4절의 현실이 이 단계에서 부딪힌다.

- 보안 담당자가 없으면 요청서의 ③은 "이 버튼을 누르세요" 수준으로.
- 개발사가 사라졌으면 코드 수정 요청 대신 완화책과 **제품 교체 권고**.
- 비용이 장벽이면 무료 조치부터.
- [클리닝 서비스](../../vol1-center/02-programs/07-portal-advisory.md) 같은 자동화 경로에 태울 수 있는 유형인지 본다.

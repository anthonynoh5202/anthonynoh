# 검증 단계: 재현이 전부다

| 레벨 | 상태 | 최종 개정 |
|---|---|---|
| 🟡 | 🔄 개정중 | 2026-10-23 |

> **한눈에 보기**
> 센터장이 "발견보다 검증"이라 한 그 검증이 이 단계다. 📎
> 재현되지 않는 취약점은 제조사도 움직이지 않고, 공지도 낼 수 없다.
> 재현은 제2편 워크스루가 가르치는 기술 그대로이며, 센터에서는 "영향 증명"까지만 하고 멈춘다.
> 대상이 남의 운영망이라 격리 재현이 불가능한 신고(상시 신고조치제, 기반시설 점검)는 증거 검토와 비파괴 확인으로 검증한다(7절).

## 1. 검증의 세 수준

| 수준 | 질문 | 산출물 | 소요 |
|---|---|---|---|
| L1 재현 | 제보대로 하면 같은 현상이 나는가 | 재현 로그, 환경 명세 | 시간 |
| L2 원인 | 왜 나는가. 어느 코드, 어느 입력 | 패치 diff 또는 코드 위치, CWE 확정 | 시간~일 |
| L3 영향 | 공격자가 실제로 무엇을 얻는가 | 최소 PoC, 영향 등급 | 일 |

급박도에 따라 멈추는 수준이 다르다. 악용 중이면 L1만 하고 공지한다. 신고포상제 평가는 L3까지 간다.

## 2. L1 재현: 환경부터

**쓰는 기술**: [실습 환경 구축](../../vol2-tech/part1-foundations/05-lab-setup.md), [동적 분석](../../vol2-tech/part2-methodology/05-dynamic-analysis.md)

- **격리된 환경**에서만 한다. 실제 서비스나 기관 시스템에 재현 시도를 하는 것은 허가 범위를 넘는다. [제1편 3부 12장 법과 제도](../../vol1-center/03-partners/12-legal.md) 대상이 운영망일 수밖에 없는 신고는 이 절이 아니라 7절의 방법으로 검증한다.
- 제보된 버전 **그대로** 설치한다. 다른 버전에서 재현 안 되면 "재현 실패"가 아니라 "버전 상이"다.
- 재현 환경을 **코드로** 남긴다. Docker Compose 한 파일이면 다음 사람이 10분 안에 같은 환경을 띄운다. [`labs/`](https://github.com/anthonynoh5202/anthonynoh/tree/main/labs) 규칙을 따른다.
- 재현 실패 시 신고자에게 **환경 명세를 보내 차이를 묻는다**. "안 됩니다"가 아니라 "이 환경에서 이렇게 했더니 이 결과입니다".

## 3. L2 원인: 패치 diff 읽기

**쓰는 기술**: [워크스루 템플릿](../../vol2-tech/part7-walkthroughs/00-overview.md) 2절, [정적 분석](../../vol2-tech/part2-methodology/04-static-analysis.md)

패치가 이미 있는 경우(N-day)가 센터 업무의 대부분이다. 패치 diff가 원인을 말해 준다.

1. 제조사 권고에서 패치 커밋 또는 버전 간 diff를 찾는다.
2. diff에서 **입력 검증이 추가된 곳**, **길이 계산이 바뀐 곳**, **권한 확인이 추가된 곳**을 본다. 그것이 취약 지점이다.
3. 그 지점에 닿는 **입력 경로**를 거꾸로 추적한다. 네트워크에서 닿는가, 인증이 필요한가.
4. 같은 패턴이 **다른 곳에도** 있는지 본다(변형, variant). 패치가 한 곳만 고쳤으면 변형이 남아 있을 수 있다. [패치 검증](../../vol2-tech/part8-reporting/03-patch-verification.md)

패치가 없는 경우(신고포상제 신규 건)는 제보의 재현 절차에서 출발해 [정적 분석](../../vol2-tech/part2-methodology/04-static-analysis.md)의 소스→싱크 추적으로 원인을 찾는다. 바이너리 제품이면 [디컴파일러](../../vol2-tech/part6-tools/02-ghidra-ida.md).

## 4. L3 영향: 어디까지 증명하는가

**쓰는 기술**: [익스플로잇 검증](../../vol2-tech/part2-methodology/06-exploit-verification.md), 각 유형 장의 5절

| 증명 수준 | 예 (SQL 인젝션) | 센터에서 필요한 경우 |
|---|---|---|
| 존재 | 에러 또는 참/거짓 차이 | 공지 최소 요건 |
| 데이터 접근 | 다른 테이블 읽기 | 신고포상제 평가, 기관 설득 |
| 변경·실행 | UPDATE, 명령 실행 | 평가위원회 Critical 판정 근거 |

**무기를 만들지 않는다.** 영향 등급 판단에 필요한 만큼만 증명한다. PoC는 실습 환경에서만 동작하도록 쓰고, 보관은 접근 통제된 곳에 🔎.

## 5. AI 결과 재검증

[AI 활용](../../vol1-center/02-programs/09-ai.md)의 "10건 중 5~6건"이 이 단계의 현실이다.

```
AI 후보 → L1 재현 시도
  ├ 재현됨      → L2로. AI 설명과 실제 원인이 같은지 확인 (다른 경우가 있다)
  └ 재현 안 됨  → 기각. 사유를 세 가지 중 하나로 기록:
                  (a) 오탐: 취약하지 않은 코드를 취약하다고 봄
                  (b) 도달 불가: 취약 코드는 맞으나 입력이 닿지 않음
                  (c) 환경 상이: 특정 설정·버전에서만 성립
```

기각 사유 (a)(b)(c)의 비율이 쌓이면 AI 점검 범위를 조정하는 근거가 된다. 기록 없는 기각은 다음 달 같은 오탐을 다시 보게 만든다.

## 6. 검증 기록

```
## 검증 기록
- 대상: 제품·버전 / 재현 환경 (labs/... 또는 명세)
- L1: 재현 성공 / 실패 (환경 차이:)  재현 명령:
- L2: 원인 코드 위치 / 패치 diff 링크 / CWE 확정 / 변형 존재 여부
- L3: 증명 수준 (존재 / 데이터 접근 / 변경·실행)  근거:
- AI 후보였다면: 유효 / 기각(a·b·c)
- 운영망 대상 신고였다면: 거친 단계 (7.1 증거 검토 / 7.2 비파괴 확인 / 7.3 복제본 재현 / 7.4 기관 확인) · 판정 (유효 / 기각 / 보류 가·나·다·라)
- 영향 등급 (잠정):   근거:
- 다음 단계: 조치 요청 담당 · 기한
```

## 7. 격리 재현이 불가능할 때: 운영망 대상 신고 🟡

2절의 원칙은 "격리 환경에서만 재현한다"이다. 그런데 상시 신고조치제([제1편 2부 6장](../../vol1-center/02-programs/06-cvd-vdp.md))의 신고는 참여 기관의 **운영 서비스**를 대상으로 하고, 기반시설 점검([제1편 2부 8장](../../vol1-center/02-programs/08-assessment-support.md))에서 나오는 것도 남의 운영 시스템이다. 취약 버전을 내려받아 설치할 수 있는 제품이 아니므로 2절의 방식이 그대로 적용되지 않는다. 그렇다고 검증을 건너뛰면 기관은 움직이지 않고 신고자는 기다린다.

이 절은 [제1편 2부 6장](../../vol1-center/02-programs/06-cvd-vdp.md) 3절의 흐름(센터가 신고를 접수해 1차 검증한다)이 맞다는 전제 위에 있다 🔎. VDP는 기관이 직접 신고를 접수하는 경우가 많으므로, 센터의 역할이 그와 다르면 이 절에서 "센터가 한다"고 쓴 일의 주체도 바뀐다.

이 경우 센터가 할 수 있는 검증은 아래 다섯 단계다. 앞 단계에서 충분하면 뒤로 가지 않는다. 각 단계의 세부 기준, 시한, 사용 시스템은 🔎 내부 운영 지침으로 대체해야 한다. 아래는 원칙만 적었다.

### 7.1 신고자 증거 검토

운영망 신고의 1차 검증은 재현이 아니라 **증거 읽기**다. 신고서에서 다음을 확인한다.

| 항목 | 보는 것 | 부족하면 |
|---|---|---|
| 요청/응답 원문 | 실제 요청과 응답의 전문(HTTP라면 헤더 포함), 또는 그에 준하는 프로토콜 로그. 화면 캡처만 있으면 부족하다 | 원문을 요청한다 |
| 타임스탬프 | 요청을 보낸 시각과 시간대. 기관 로그와 대조할 수 있는 유일한 열쇠 | 시각과 출발지를 요청한다 |
| 재현 절차의 구체성 | 어느 경로·파라미터·값에서, 어떤 조건(인증 여부, 계정 종류)으로. 제3자가 그대로 따라 할 수 있는가 | 단계별 보완을 요청한다 |
| 영향 범위 주장의 근거 | "전체 열람 가능"이라면 그 근거가 무엇인가. 실제로 본 것과 추정한 것을 구분한다 | 실제 확인된 범위만으로 잠정 판정한다 |
| 허용 정책 준수 | 신고자의 행위가 기관이 공개한 허용 정책 안이었는가 | 밖이었다면 [제1편 3부 12장](../../vol1-center/03-partners/12-legal.md) 🔎 허용 범위 밖 신고의 처리 지침 |

신고자가 운영망에서 실제 데이터를 추출했다고 주장하면 그 자체가 허용 정책 위반일 수 있다. 증거는 보관하되 센터가 같은 행위를 반복하지 않는다.

### 7.2 허용 정책 범위 안에서의 비파괴 확인

센터가 직접 확인할 때의 원칙이다.

- **센터의 확인도 기관이 공개한 허용 정책 범위 안에서만 한다.** 센터 소속이라는 사실이 범위를 넓히지 않는다. 🔎 센터 직원의 확인 행위에 적용되는 내부 규칙(사전 통보 여부, 사용 계정, 출발지 등록).
- **존재 확인 수준에서 멈춘다.** 4절의 "존재" 단계까지다. 데이터 접근·변경·실행 단계의 증명은 운영망에서 하지 않는다.
- **데이터를 바꾸거나 꺼내지 않는다.** 읽기 전용 요청으로, 필요한 최소 횟수(원칙적으로 1회)만 보낸다.
- **가용성에 영향을 줄 수 있는 요청을 보내지 않는다.** 대량 스캔, 시간 지연 기반 기법의 반복, 자원을 소모하는 입력은 하지 않는다.
- **모든 요청을 기록한다.** 시각, 출발지, 요청 내용, 응답. 기관 로그에 센터의 요청이 남으므로 사고로 오인되지 않도록 🔎 사전 통보 채널을 쓴다.

비파괴의 경계를 예로 들면 다음과 같다.

| 구분 | 예 |
|---|---|
| 허용 | 존재 확인을 위한 읽기 전용 요청 1회(예: 참/거짓 응답을 비교하는 한 쌍의 요청), 버전 배너·응답 헤더 확인 |
| 금지 | 데이터 추출·변경, 시간 지연 기반 기법의 반복, 인증 우회 뒤의 탐색, 가용성에 영향을 주는 요청(대량 스캔, 자원을 소모하는 입력) |

이 표는 기술적 경계다. 법적 경계는 별개다. 센터 직원은 시범사업에 등록된 참여 화이트해커가 아니므로, 기관 허용 정책의 조건부 보호가 센터 직원의 확인 행위에도 미치는지는 🔎 법무 확인이 필요하다([제1편 3부 12장 2절](../../vol1-center/03-partners/12-legal.md)).

### 7.3 동일 제품의 격리 복제본

운영 서비스가 상용 제품이나 오픈소스 위에 있고 신고가 그 제품의 결함이라면, 같은 버전을 격리 환경에 설치해 2절의 방식으로 재현한다. 이 경우 검증 결과는 "제품 수준에서 재현됨"이며 해당 기관의 설정에서도 성립하는지는 7.4로 확인한다. 기관 고유의 코드가 원인이면 복제본을 만들 수 없다. 기관이 스테이징·테스트 환경을 제공하면 거기서 재현한다. 🔎 기관에 테스트 환경 제공을 요청할 수 있는 근거와 절차.

### 7.4 기관 담당자에게 확인 요청

센터가 할 수 없는 확인은 기관에 요청한다. 무엇을 어떻게 확인해 달라는지 구체적으로 적어야 회신이 온다.

```
## 확인 요청 (운영망 대상 신고)
- 식별번호:
- 대상: 서비스 / 경로·엔드포인트 / 영향이 추정되는 구성요소
- 신고 요지 (한 문장):
- 확인해 주실 것:
  1. 로그: [시각, 시간대] 전후 [출발지]에서 [엔드포인트]로의 요청 유무, 응답 코드와 크기
  2. 동작: 첨부한 요청을 테스트 환경 또는 허용된 조건에서 보냈을 때 응답이 신고와 같은지
  3. 구성: 해당 기능의 제품·버전·설정 (인증 적용 여부, 입력 검증 위치 등)
  4. (선택) 로그 제공: 1의 구간에 해당하는 로그 원문을 센터에 보내 주실 수 있는지
- 센터가 이미 확인한 것 (7.1~7.3 결과):
- 회신 희망 기한: 🔎
- 유의: 운영망에서 데이터 변경·추출을 수반하는 확인은 요청하지 않는다.
        이 정보의 공유 범위는 [4장 2절](04-advisory.md)의 등급 표시를 따른다.
```

기관에 로그 대조를 맡길 인력이 없거나 회신이 모호하면, **기관 로그를 받아 센터가 직접 대조하는** 선택지가 있다. 신고자가 제출한 요청의 시각·출발지·경로를 기관 로그에서 찾아 응답 코드와 크기를 맞춰 보는 일로, 침해대응의 로그 분석 기법이 그대로 쓰인다. 🔎 로그 반출의 근거와 개인정보 처리 절차.

### 7.5 "유효"로 판정할 수 없을 때

판정은 유효, 기각, **보류** 셋이다. 보류는 기각이 아니다. 사유를 다음 넷 중 하나로 기록한다. 5절의 AI 후보 기각 사유 (a)(b)(c)와 다른 목록이므로 기호를 한글로 구분한다.

```
(가) 증거 불충분   신고자에게 보완을 요청한 상태
(나) 확인 불가     허용 정책 범위 밖이거나, 비파괴 확인으로는 존재를 가릴 수 없음
(다) 기관 회신 대기 7.4 요청을 보낸 상태
(라) 환경 없음     복제본도 테스트 환경도 없음
```

- 신고자에게 상태와 사유를 알린다. "검토 중"만으로는 신고자가 떠난다.
- 악용 가능성이 높은 보류 건은 검증 완료를 기다리지 않고 기관에 **잠정 통보**한다. 악용 중 건은 L1만 하고 공지한다는 1절의 원칙과 같은 논리다.
- 🔎 보류 시한, 시한 경과 시 처리(재요청, 기각 전환), 보류 건의 포상·공개 처리.
